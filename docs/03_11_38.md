## 1. 먼저 밝혀둘 것 — 이번 수치는 이전 보고서와 직접 비교할 수 없다

이전 보고서(`web-check-2026-09-03.md`)의 **65점 / FCP 5.1초 / LCP 6.2초** 는
**PageSpeed Insights API**(구글 서버에서 측정)로 잰 값이다.

**이 PC 에서 로컬 Lighthouse 13.4.1** 로 측정했다.

측정 기계가 다르면 점수도 달라진다. 따라서 아래 "이전" 칸과 "이후" 칸을

## 3. 구조 변화 — 이것은 측정 도구와 무관하게 확인된다

이번 작업이 노린 것은 점수 자체가 아니라 **렌더링을 막는 요청과 외부 접속 사슬**이었다.
그 부분은 도구가 달라도 그대로 읽힌다.

| | 이전 | 이후 |
|---|---|---|
| 렌더링을 막는 요청 | **4개** (jsdelivr Pretendard · jsdelivr Paperlogy · Google Fonts 2) + 앱 CSS | **1개** (앱 자체 CSS 22KB, 같은 도메인) |
| 접속하는 외부 도메인 | 3곳 (jsdelivr · fonts.googleapis · fonts.gstatic) | **0곳** |
| 전체 요청 23건의 출처 | 외부 CDN 섞임 | **전부 `portfolio-heebon.vercel.app`** |
| 폰트 요청 | 외부 gstatic·jsdelivr | 같은 도메인 woff2 14건 |
| 네트워크 의존 사슬 | HTML → 외부 CSS(도메인 3곳, 각각 DNS+TLS) → 외부 woff2 | HTML → 자체 CSS → 자체 woff2 |

**외부 도메인 접속 사슬은 완전히 사라졌다.**

## 4. 정확한 비교를 하려면

같은 조건(PageSpeed Insights)으로 다시 재야 한다. 두 가지 방법이 있다.

1. **할당량이 회복된 뒤 다시 측정** — PSI 무료 할당량은 하루 단위다. 말해주면 다시 재겠다.
2. **PSI API 키를 발급받아 쓰기** — 키가 있으면 할당량 문제가 없다.
   `console.cloud.google.com` 에서 PageSpeed Insights API 키를 만들어 주면
   `node check/scripts/check.mjs <URL> --psi-key <키>` 로 바로 잰다.

**둘 중 무엇도 하기 전까지, 65점이 몇 점이 됐는지는 "확인 안 됨" 이다.**

## 5. 이제 가장 큰 걸림돌은 폰트가 아니다 — LCP 이미지다

폰트가 빠지고 나니 남은 병목이 뚜렷해졌다. `lcp-discovery-insight` 결과다.

LCP 요소는 **히어로 인물 사진**(`hero-portrait.webp`, `#m-hero` 안의 `<img>`)인데,

| 점검 항목 | 결과 |
|---|---|
| `fetchpriority=high` 가 붙어 있는가 | **아니오** |
| 최초 HTML 문서에서 발견 가능한가 | **아니오** |
| `loading=lazy` 를 안 쓰는가 | 예 (문제 없음) |

**"최초 HTML 에서 발견 불가"** 가 핵심이다. 이 사이트는 React SPA 라서
그 이미지가 `index.html` 에 없고, JS 가 실행된 뒤에야 나타난다.
브라우저는 JS 를 받아 돌릴 때까지 그 사진의 존재를 모르고, 그만큼 LCP 가 늦어진다.

이전 보고서 7장의 **4번 항목**(`preload` + `fetchpriority="high"`)이 바로 이것이고,
이제 그게 1순위가 됐다.

그 다음은 `unused-javascript` / `bootup-time` — JS 번들 382KB 지연 로딩인데, 품이 크고 효과는 작다.
