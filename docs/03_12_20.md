# LCP 이미지 개선 — 작업과 결과 (2026-09-03 12:20)

배포 커밋: `60ea063` — "perf: LCP 이미지(히어로 인물 사진)를 최초 HTML 에서 발견되게 한다"
대상: `https://portfolio-heebon.vercel.app`

---

## 요약 — 먼저 말해둘 것

**감사 항목은 고쳐졌지만, LCP 시간은 줄지 않았다.**
지시받은 작업은 정확히 수행했고 의도대로 동작하는 것도 확인했으나,
**성능 점수와 LCP 는 움직이지 않았다.** 이유는 4장에 적었다.

---

## 1. 무엇을 고쳤나

`index.html` 에 LCP 이미지를 미리 받는 한 줄을 넣고, `<img>` 에 우선순위를 붙였다.

| 파일 | 내용 |
|---|---|
| `index.html` | `<link rel="preload" as="image" fetchpriority="high" href="…hero-portrait.webp">` 추가 |
| `src/components/SafeImage.jsx` | `priority` 프롭 추가 → `loading="eager"` + `fetchpriority="high"` |
| `src/sections/Hero.jsx` | 히어로 사진에 `eager` → `priority` |
| `src/sections/mobile/MobileHero.jsx` | 같음 |

`index.html` 에는 **소스 경로**(`/src/assets/images/hero-portrait.webp`)를 적어두었다.
빌드하면 Vite 가 해시 붙은 실제 경로(`/assets/hero-portrait-CNfrO15O.webp`)로 바꿔준다 —
직접 확인했고, 그래서 별도 플러그인은 만들지 않았다.

---

## 2. 의도대로 동작하는가 — 예

Lighthouse `lcp-discovery-insight` 항목이 **0점 → 1점(통과)** 으로 바뀌었다.

| 점검 항목 | 이전 | 이후 |
|---|---|---|
| `fetchpriority=high` 가 붙어 있는가 | 아니오 | **예** |
| 최초 HTML 문서에서 발견 가능한가 | 아니오 | **예** |
| `loading=lazy` 를 안 쓰는가 | 예 | 예 |

헤드리스 Chrome 확인 결과도 같다.

- `hero-portrait` 요청 **1건** — preload 와 `<img>` 가 같은 요청을 공유한다(중복 내려받기 없음)
- 요청 우선순위 **High**, initiator **parser** (= 최초 HTML 을 읽다가 발견했다는 뜻)
- **이미지가 시작되는 시점이 95ms 앞당겨졌다** — `Resource load delay` 113ms → 18ms
- 콘솔 에러 0, 네트워크 실패 0

---

## 3. 그런데 성능 수치는 그대로다

같은 PC · 같은 도구(로컬 Lighthouse 13.4.1) · 같은 설정(모바일)으로 각 3회.

| 구분 | 성능 | LCP | JS 실행(bootup) | 메인스레드 총작업 | TBT |
|---|---|---|---|---|---|
| 이전 | 70 | 4.91s | 4908ms | 6846ms | 0ms |
| 이전 | 68 | 4.68s | 4843ms | 6666ms | 339ms |
| 이전 | 68 | 4.68s | 5209ms | 7139ms | 346ms |
| 이후 | 70 | 4.81s | 6238ms | 8237ms | 137ms |
| 이후 | 67 | 4.66s | 6050ms | 7958ms | 364ms |
| 이후 | 63 | 4.75s | 5753ms | 7738ms | 477ms |
| **중앙값 이전** | **68** | **4.68s** | 4908ms | | |
| **중앙값 이후** | **67** | **4.75s** | 6050ms | | |

**차이는 회차 간 흔들림보다 작다.** 개선됐다고도, 나빠졌다고도 말할 수 없다.
`bootup` 이 이후 회차에서 더 큰 것도 이번 변경 탓이 아니다 —
JS 번들 크기는 382.28kB 로 **양쪽이 완전히 같다.** 측정 기계의 상태 차이다.

(CLS 가 0.000 → 0.005 로 잡힌 회차가 있으나, 기준선 0.1 에 한참 못 미치는 값이다.)

---

## 4. 왜 안 줄었나 — 확인된 원인

LCP 시간을 네 단계로 쪼개면 이렇다.

| 단계 | 이전 | 이후 |
|---|---|---|
| 서버 첫 응답 (TTFB) | 29ms | 29ms |
| **이미지 요청이 시작되기까지** | 113ms | **18ms** ← 이번 작업이 줄인 부분 |
| 이미지 내려받기 | 27ms | 30ms |
| **요소가 화면에 그려지기까지 (render delay)** | 228ms | 588ms |

**이번 작업이 줄일 수 있었던 몫은 113ms 중 95ms 뿐이었다.**
사진 파일은 40KB 라 내려받는 데 30ms 밖에 안 걸린다. 애초에 병목이 아니었다.

진짜 병목은 마지막 줄 **"요소가 화면에 그려지기까지"** 다.
이 사이트는 React SPA 라서, 사진 파일이 아무리 일찍 도착해도
**JS 를 받아 파싱하고 실행해서 React 가 그 `<img>` 를 만들어 붙이기 전에는 그려질 수 없다.**
모바일 기준(CPU 4배 감속)에서 JS 실행에만 **5~6초**가 걸린다.

Lighthouse 도 이 점을 알고 있었다. 고치기 **전부터** 이 감사 항목의
예상 절감치를 `LCP: 0ms` 로 내놓고 있었다. 즉 "이건 안 좋은 패턴이니 고쳐라"라고
말한 것이지, "고치면 몇 초 빨라진다"고 말한 게 아니었다.

**이전 보고서(03_11_38.md)에서 이것을 1순위로 꼽은 것은 내 판단 착오였다.**
`lcp-discovery-insight` 가 실패 항목이라는 것만 보고 절감 예상치를 함께 읽지 않았다.

---

## 5. 그럼 이 작업은 헛수고였나 — 아니다, 다만 기대는 조정해야 한다

- 감사 항목은 실제로 잘못된 상태였고, 지금은 바르게 고쳐졌다.
- 이미지가 95ms 일찍 출발하는 것도 사실이다.
- JS 가 캐시돼 있는 재방문이나 빠른 기기에서는 이 몫이 상대적으로 더 크게 남는다.
- 되돌릴 이유는 없다. 다만 **이것으로 점수가 오르지는 않는다.**

---

## 6. 이제 남은 것은 JS 번들 하나다

수치가 가리키는 곳은 뚜렷하다.

| 항목 | 값 |
|---|---|
| JS 번들 | 382KB (gzip 128KB) |
| JS 실행 시간 (`bootup-time`) | 4.8 ~ 6.2초 |
| 메인스레드 총작업 | 6.7 ~ 8.2초 |
| `unused-javascript` | 0점 |

첫 화면에 필요 없는 코드(GSAP 스크롤 연출, 하단 섹션들)를 나중에 불러오면
JS 실행 시간이 줄고, 그만큼 render delay 가 줄어 **LCP 가 직접 내려간다.**

원래 보고서에서 이걸 "품이 크고 효과는 작다. 나중에" 로 적었는데,
**폰트와 이미지가 정리된 지금은 이것이 유일하게 남은 큰 지렛대다.** 순서가 바뀌었다.

다만 이 사이트는 GSAP 스크롤 연출이 화면 대부분을 차지하므로,
코드를 쪼개면 **연출이 늦게 붙어 첫 스크롤이 어색해질 위험**이 있다.
작업 전에 어디까지 미룰지 정해야 한다.
