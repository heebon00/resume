## 1 - HTML 문법

### 1-1. URL 검사 — 오류 0건 (의미 없음)

W3C가 받은 것은 `index.html` 원본 33줄이 전부다. React가 그리기 전이라 본문이 없다.

```html
<body>
  <div id="root"></div>
</body>
```

**"오류 0건"은 이 빈 껍데기에 대한 판정이다.** 실제 화면의 마크업은 검사되지 않았다.

경고 9건은 `<meta … />`, `<link … />`의 끝 슬래시다(`Trailing slash on void elements has no effect…`). HTML에서 빈 요소의 `/`는 의미가 없다. 이 프로젝트는 모든 속성값에 따옴표를 쓰므로 실제 위험은 없다. **고치지 않아도 무방하다.**

### 1-2. 렌더링된 DOM 검사 — 오류 10건 (실제 결과)

헤드리스 Chrome으로 렌더링을 마친 DOM(143 KB)을 떠서 같은 검사기에 넣은 결과다.

| 건수 | 무엇이 잘못됐는가 | 어떻게 고치는가 |
| --- | --- | --- |
| 1 | 보이는 `<main>` 요소가 2개다 (`A document must not include more than one visible "main" element.`) | 문서에 `<main>`은 하나여야 한다 |
| 9 | `id` 중복: `hero`, `about`, `experience`, `gallery`, `projects`, `keywords`, `design`, `skills`, `contact` (`Duplicate ID "…"`) | `id`는 문서 전체에서 유일해야 한다 |

**원인 (확인됨)** — `src/App.jsx`가 데스크톱과 모바일 레이아웃을 **둘 다 DOM에 렌더링하고, CSS 클래스로만 하나를 숨긴다.**

```jsx
// src/App.jsx:65
<div className="xl:hidden">      {/* 1280 미만 */}
  <MobilePage />                  {/* 안에 <main> + id="hero" … */}
</div>

// src/App.jsx:70
<main className="relative hidden w-full xl:block">   {/* 1280 이상 */}
  {/* 안에 id="hero" … 같은 id 9개 */}
</main>
```

- `src/sections/mobile/MobilePage.jsx:31` 이 `<main>`을 하나 더 연다 → `<main>` 2개
- 모바일 9개 섹션(`MobileHero.jsx:16` 등)이 데스크톱 섹션(`Hero.jsx:48` 등)과 **같은 `id`를 쓴다** → 중복 9건

`xl:hidden` / `hidden`은 Tailwind **클래스**이지 HTML `hidden` **속성**이 아니다. 검사기는 CSS를 적용하지 않으므로 둘 다 "보이는" 것으로 판정한다. 브라우저에서는 하나만 보이지만, **DOM에는 항상 둘 다 있다.**

**실제로 무엇이 문제인가**

1. `#projects` 같은 앵커 링크는 항상 **문서에 먼저 나오는 쪽(모바일)** 으로 이동한다. 데스크톱 화면에서는 숨겨진 요소로 점프하는 셈이다.
2. `document.getElementById()` 도 항상 모바일 쪽을 집는다.
3. 보조기기가 `<main>` 2개를 만나 문서 구조를 잘못 읽을 수 있다.

Lighthouse 접근성 100점에는 이 항목이 잡히지 않았다. **자동 점수가 표준 준수를 보장하지 않는다는 예다.**

**선택지**

1. 화면 폭에 따라 **한쪽만 마운트**한다 — DOM이 절반으로 줄어 성능에도 도움. 다만 리사이즈 시 재마운트되고 GSAP 초기화가 다시 돌아 연출에 영향이 갈 수 있다
2. 모바일 쪽 `id`에 접두사를 붙이고(`m-hero` 등) `<main>`을 하나로 정리한다 — 가장 작은 변경. 앵커 링크 대상도 함께 맞춰야 한다
3. 그대로 둔다 — 화면은 정상 동작한다. 표준 위반과 앵커 오작동은 남는다

## 2 - CSS 문법

W3C CSS Validator가 오류 55건을 보고했으나, **확인 결과 55건 전부 검사기가 최신 CSS를 모르는 데서 온 오탐이다.** 실제 문법 오류가 아니다.

| 건수 | 검사기 메시지 | 실제 정체 | 판정 |
| --- | --- | --- | --- |
| 51 | `Unrecognized at-rule "@property"` | Tailwind v4가 생성하는 등록 커스텀 속성(`--tw-translate-x` 등) | **오탐.** `@property`는 표준이며 전 세계 지원율 94.87% (Chrome 85+, Firefox 128+, Safari 16.4+) |
| 1 | `Property "margin-trim" doesn't exist` | Tailwind v4의 브라우저 판별용 `@supports ((-webkit-hyphens: none) and (not (margin-trim: inline))) …` 안에 있다 | **오탐.** 스타일 선언이 아니라 기능 검사식이다. `margin-trim` 미지원(Safari 전용, 15.49%)을 **일부러 조건으로 쓴다** |
| 1 | `Property "container-type" doesn't exist` | `src/index.css:123` `container-type: inline-size` | **오탐.** 컨테이너 쿼리 표준 속성이며 이 프로젝트의 `--u` 단위 체계가 여기에 의존한다 |
| 1 | `Unknown dimension` (`:root`) | `--u: 0.0520833cqw` 의 `cqw` 단위 | **오탐.** 컨테이너 쿼리 단위. 위 `container-type`과 한 쌍이다 |
| 1 | `Parse Error` (`:root`) | 위 `cqw`를 못 읽어서 이어서 난 파생 오류 | **오탐** |

W3C Jigsaw 검사기는 CSS Level 3 프로파일 기준이라 컨테이너 쿼리·`@property` 같은 이후 표준을 모른다.
**고칠 것 없음.** 고치면 오히려 레이아웃이 깨진다.

2. **`<meta name="description">` 추가** — 한 줄이면 되고, 검색 최적화가 91 → 100점이 된다. 내용은 본인이 정해야 한다.
3. **외부 폰트 CSS 4개를 비차단으로 전환** — FCP 5.1초 / LCP 6.2초를 줄이는 가장 큰 지렛대이며, 성능 65점의 35%를 차지하는 두 지표를 함께 움직인다. 폰트를 프로젝트에 내려받아 자체 호스팅하면 CDN 3곳 접속 사슬도 같이 사라진다.
4. **LCP 이미지에 `preload` + `fetchpriority="high"`** — 3번을 하고 나서 다시 재면 효과가 명확해진다.
5. 번들 지연 로딩(`unused-javascript`) — 위보다 품이 크고 효과는 작다. 나중에.

3·4를 하면 성능은 오르지만, **몇 점이 될지는 재 봐야 안다.** 미리 단정하지 않는다.

## 검사 도구와 한계

이 보고서는 W3C Nu HTML Checker, W3C CSS Validator, ESLint(recommended), Lighthouse 결과를 옮긴 것입니다. 문법 검사는 코드가 규칙에 맞는지만 보므로, 문법이 맞아도 화면이 의도와 다르게 보일 수 있습니다. 린트는 자주 나오는 실수 위주로 잡으며, 팀 관습이나 프로젝트별 규칙까지는 판단하지 않습니다. 성능 점수는 잴 때마다 몇 점씩 달라지므로 한 번의 값으로 판단하지 않습니다.

**이 사이트가 React SPA라서 생기는 한계를 특히 유의합니다.** 네 검사기 중 실제로 화면을 본 것은 Lighthouse뿐입니다.

| 검사 | 자바스크립트 실행 | 이 프로젝트에서 유효한가 |
| --- | --- | --- |
| W3C HTML (URL) | 안 함 | **아니오** — 빈 셸만 봄. 그래서 렌더링 DOM으로 다시 검사함(1-2장) |
| W3C CSS | 해당 없음 | 예 — 빌드된 CSS 파일을 직접 받아 검사 |
| ESLint | 해당 없음 | **아니오** — 압축 번들을 검사. 원본 판정은 oxlint |
| Lighthouse | **함** | 예 — 실제 브라우저로 렌더링해 측정 |

그 밖에 덧붙일 것.

- CSS 오류 55건은 검사기가 최신 표준을 모르는 오탐입니다. `@property`·`container-type`·`cqw`의 실제 지원 현황은 caniuse에서 따로 확인했습니다.
- JS 린트 1,286건은 압축된 배포 번들을 검사한 결과라 사람이 고칠 대상이 아닙니다. 원본 기준 판정은 oxlint 0건입니다.
- 렌더링 DOM 검사는 데스크톱 폭 기준 한 번만 떴습니다. 모바일 폭에서만 나타나는 마크업 문제가 더 있는지는 **확인되지 않았습니다.**
